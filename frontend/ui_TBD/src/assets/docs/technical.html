RAG Finance Assistant — Technical Documentation

How the retrieval-augmented generation pipeline parses, chunks, embeds, retrieves, and is evaluated.

1 Pipeline Overview

A source policy document is parsed into text, split into overlapping chunks, embedded with a sentence-transformer model, and stored in a vector database. At query time the user's question is embedded the same way, the most similar chunks are retrieved by cosine similarity, and an LLM composes a grounded answer with citations back to the source passages.

2 Parsing

Text is extracted from the source .docx document(s) configured in DOCUMENTS. The extracted plain text is normalized before chunking. Additional documents (e.g. Org_HR_Policy.docx) can be ingested by extending the DOCUMENTS list.

3 Chunking

Character-based chunking with a fixed overlap so context isn't lost across chunk boundaries.

ParameterValueNotes
Chunk size900 charactersTarget size per chunk
Chunk overlap150 charactersShared between adjacent chunks

4 Embedding

Chunks and queries are embedded with the HuggingFace sentence-transformers model BAAI/bge-small-en-v1.5, producing 384-dimensional vectors.

PropertyValue
ModelBAAI/bge-small-en-v1.5
Dimensions384
Similarity metricCosine
Query instruction prefix"Represent this sentence for searching relevant passages: "
BGE retrieval models are trained with an instruction prefix on the query side only. Prefixing the query (not the stored passages) measurably improves retrieval quality.

5 Vector Store & Retrieval

The active backend is selected with the VECTOR_DB environment variable (chroma by default, or pinecone). Both use cosine distance over 384-dimensional vectors.

At query time the top 4 most similar chunks (TOP_K, overridable via RAG_TOP_K) are retrieved and passed to the LLM as grounding context.
